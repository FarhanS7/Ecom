# T027b: Seller console data access, validation, and server actions

- Module: [catalog](../../docs/modules/catalog.md)
- Phase: [Catalog and storefront](../phases/02-catalog-storefront.md)

- Branch: `feature/catalog/t027-build-seller-catalog-editing-screens`

## Goal

The seller console's server-side layer: cookie-carrying uncached reads, shared
contract validation with field errors, and server actions that turn API outcomes
into form state (including the version-conflict recovery path).

## Acceptance criteria

- [ ] `features/seller/load.ts` (server-only): membership, product list, one
      product, and variants — `cache: 'no-store'`, the browser's cookies
      forwarded, bodies validated with the real contracts, and no crash when the
      API is absent (unavailable, not "not found").
- [ ] `features/seller/validation.ts` (pure): FormData/JSON values → contract
      schemas, returning field-keyed errors and the ENTERED values so a rejected
      form is never emptied (`frontend.md`: "preserves entered data after server
      rejection").
- [ ] `features/seller/client.ts` (server-only): the seller write calls, mapping
      201/200 → ok, 404 → not-found (unknown store/product or no permission —
      indistinguishable by design), 409 → conflict (with a re-read of the current
      product for "reload/reapply"), 401 → unauthenticated, other → unavailable.
- [ ] `features/seller/actions.ts` (`'use server'`): create/update product,
      create/update variant, publication toggle, archive — each validated
      server-side before the call, returning typed state for the UI.
- [ ] No gateway allowlist change: the browser never reaches the seller write
      API (ADR-0010 decision 5); the gateway keeps refusing those paths.
- [ ] Unit tests for validation and the client mapping (ok/404/409/401/5xx,
      and that a variant write re-reads the product version).

## Verification

Web unit tests, lint, typecheck, web build. The UI half is [T027c](T027c.md).
