# T028b: Catalog, theme, and publication generators plus verification

Parent: [T028](T028.md) (split per its scope rule; T028 stays the parent ID).

- Module: [catalog](../../docs/modules/catalog.md)
- Phase: [Catalog and storefront](../phases/02-catalog-storefront.md)
- Dependencies: [T028a](T028a.md)
- Branch: `feature/catalog/t028-seed-a-deterministic-catalog-skeleton`

## Goal

A Tier S catalog that a human can actually browse: a category tree, products with
variants and prices, per-channel publication that agrees with product status, a
validated theme per store, and a verifier that can state what was seeded.

## Acceptance criteria

- [x] `catalog.ts`: `planCatalog(identity, options)` returns plain rows for
      categories (a real tree with `/parent/child/` paths built by the service's
      own `buildCategoryPath`), products (unique slug per store, `seed-` prefixed,
      deterministic ids), variants (active and inactive, log-normal prices), and
      publications.
- [x] `min_price_cents` equals the cheapest ACTIVE variant's price — derived, never
      an independent random number (the T019 invariant). Asserted from the plan in
      `catalog.test.ts` and from the DATABASE in `verify.ts`.
- [x] Visibility is derived, never assumed: the plan records which products are
      visible per channel (`active` AND the channel flag), and separately records
      the ADR-0010 cases that MUST stay invisible — a draft carrying a channel flag
      ("on (not live)") and an archived product carrying flags. The unit suite
      asserts the visible sets contain only active products and that the recorded
      draft/archived ids are absent from them. Store 0 is both-channel, the last
      catalogued store is store-channel-only, and the empty store covers the
      empty-state path.
- [x] `themes.ts`: theme tokens per store validated against the shared contract
      (`themeTokensSchema.parse`, so an invalid token throws at plan time), plus
      `store_content` whose `featured_ids` reference products of THAT store and are
      drawn only from what the store channel can show; the empty store features
      none. `socials`/`swatches` are left empty rather than inventing a shape
      T068 will own.
- [x] `verify.ts`: `planChecksums`/`planChecksum` (pure) and `databaseChecksums`/
      `databaseChecksum` (live) — stable digests over domain columns only.
      `password_hash` is excluded structurally, and a unit test proves that
      changing a user's hash does not change the digest. `verifyDatabase` returns
      per-table counts, 15 named referential-integrity checks, distribution facts,
      and a `failures` list.
- [x] `seed.ts` writes the plan in FK order inside bounded chunks (250-row batches),
      idempotently (`ON CONFLICT DO NOTHING` on the deterministic PKs) and reports
      how many rows each table actually INSERTED, so a second run can be observed
      to add zero rows.
- [x] Root `pnpm seed:verify` script exists (`… db:seed -- --verify`) and reports
      counts, per-table checksums, distribution facts, and the 15 FK checks; it
      exits non-zero when any check fails. Verified on this host that
      `pnpm seed:verify` reaches the parser (`Verifying seeded data: size=s,
      seed=42`) and that an unsupported size is still refused before connecting.
- [x] Unit tests for the pure planners: determinism (same seed → same plan and
      same checksum), sensitivity (a different seed → a different checksum),
      scoped-unique slugs/SKUs, derived `min_price_cents`, publishability, the
      invisible draft/archived cases, channel shapes, and theme validity.
- [x] The commands doc line for `seed:verify` ("counts/FKs/distributions/ledger")
      is honoured for counts/FKs/distributions; the ledger half is printed as not
      applicable until orders exist (T077).
